And **SOS never dials**: the server flags the trip, mints a link and pushes to the emergency contacts who are GojoGo accounts, then hands the local emergency number back for the *phone* to call — a backend placing an emergency call is a claim about integration with emergency services this system has not earned. **All of Phase 3 is live and none of M5 has been exercised in production yet** — the invitation listener, the reward out of STAKING and the public `GET /v1/share/{token}` have never run against a real trip. **Phase 4 M1 (real couriers) followed on 2026-08-02**, and it is the milestone that finishes a promise made two milestones earlier in two separate places: 2b M4 built delivery's fulfilment as a real state machine walked by a *simulated* timeline, saying dispatch would replace only that job — and it did, with the six statuses, both events and every customer endpoint unchanged; and 2e M3 settled the courier's fee and tip to the platform under their own ledger kinds rather than folding them into commission, so paying a real courier is a payee and not an archaeology project. Three things to carry forward. **A platform module was not touched at all** — `delivery` hung its courier assignment off the same `DispatchAssigned` / `DispatchExhausted` events `travel` uses, which is exactly what `travel`'s listener predicted in a comment, and is the return on events rather than callbacks. **Deleting a simulation costs a surface**: the fulfilment job was the only thing that ever moved an order, so the milestone had to give a restaurant a queue with an accept, a prep estimate and a reject — the kitchen had to become a person before the courier could. And **the state machine did not grow a word**: "the food is cooking and nobody has taken the delivery" is a column beside the status rather than a seventh one, because it is a problem with an order rather than a stage of it. **Phase 4 M2 (handoff integrity + money) followed on 2026-08-02** and is the milestone that puts evidence behind M1's two unwitnessed taps — a pickup code the kitchen displays and the courier types, a delivery PIN or a contactless proof photo, the courier↔customer thread, and the first way a driver or courier can get their earnings out of the platform at all. Four things to carry forward. **The pickup code runs the opposite way to SPECS §5** — the merchant shows, the courier types — because the party who must act should be the party with the incentive, and a courier can only learn that code by standing at that counter, which is the whole fact it certifies. **A wrong code is a 200 carrying the attempts left**, not an error: a courier who mistyped a digit has not made a bad request, and it is also the only shape in which the attempt counter *commits* rather than being rolled back with the exception. **The counting is deliberately asymmetric** — never at the counter, where the merchant is standing right there and a lockout would strand somebody holding food; always at the door, where the risk is a delivery being marked done that never happened — and reaching the limit opens a photo fallback rather than a dead end, a hole that is documented rather than denied. And **the worker payout surface belongs to `dispatch`**, one surface for drivers and couriers because a dual-mode person has one balance, which surfaced the fact a merchant payee had hidden: a worker is paid into their own `USER AVAILABLE` bucket, the same pocket a card top-up lands in, so a withdrawal over a raw balance would be this platform's first card→bank path and is capped at what the person actually earned. **Phase 4 M3 (multi-merchant orders) followed on 2026-08-04**, and **Phase 4 M4 (pickup / collect-in-store) the same day** — the gap this document, the vision and §9's storefront `info` block had all assumed was already filled. Two things to carry forward from M4. **Collection is a fulfilment *kind* rather than a delivery with a zero courier**, which is what keeps it to one branch in three places instead of a null courier special-cased through every screen, receipt and dispatch call; and the kind belongs to the **order**, not the sub-order, because a mixed order would have to decide whether it is finished when the courier is done or when the customer eventually walks to the other counter, with one hold and one settlement to answer that with. And **the handoff code inverts under one rule**: M2 had the kitchen show and the courier type because a courier cannot be paid until the step is done; on a collection the payee is behind the counter, so the customer shows and the kitchen types — *the code is displayed to the party that does not type it, and typed by the party who is paid for completing the step.* Next in sequence: the rest of M4's breadth, scheduled orders first (a scheduled pickup is the same poller without `pickupLead`) — or, ahead of it, the exercising that Phase 3 M5, Phase 4 M1–M4 and Phase 2f are all still waiting on.

## 1. Guiding principle

**Modular monolith now, microservices later — only when forced to.** One deployable Spring Boot application, internally split into modules that never share database tables, never call each other's internals directly, and communicate only through public interfaces and domain events. This gets almost all the benefit of microservices (clean boundaries, independent reasoning, safe parallel work) without the operational cost (N deployments, N databases, service-to-service auth, a gateway) before that cost is justified.

Scalability comes from statelessness + horizontal scaling + caching, not from splitting services. A stateless Spring Boot monolith behind a load balancer, with Redis caching and read replicas, scales to very large traffic before any module needs to become its own service.

**When to actually split a module out**, and not before:
- A workload needs different scaling/hardware than the rest (video transcoding; geo-dispatch needing low-latency co-located Redis).
- A module's failure mode must not take down everything else (messaging crashing shouldn't break checkout).
- A team boundary forms and independent deploy cadence is needed (not relevant solo, relevant once you hire).

## 2. Shape of the system: platform + verticals

GojoGo is a **superapp**. A flat list of equal modules under-explains how the iOS client is already structured (`AppNavMode.myWorld` vs `.collections`). Prefer this mental model:

```
┌─────────────────────────────────────────────────────────────┐
│                     PLATFORM (shared)                        │
│  identity · media · messaging · notifications · payments     │
│  dispatch · search                                           │
└─────────────────────────────────────────────────────────────┘
          ▲ used by ▼
┌─────────────────────────────────────────────────────────────┐
│                   VERTICAL PRODUCTS                          │
│  social · watch · travel · delivery · economy · services     │
│  partner · assistant                                         │
└─────────────────────────────────────────────────────────────┘
```

| Layer | Modules | Role |
|---|---|---|
| **Platform** | `auth`/`identity`, `kyc`, `media`, `music`, `messaging`, `notifications`, `payments` (incl. **GoJo Wallet**), `dispatch`, `search` | Reusable capabilities. Verticals compose these; they do not re-implement chat, push, geo-matching, uploads, or money movement. |
| **Verticals** | `social`, `watch` (catalog UX on `media`), `travel`, `delivery`, `economy`, `services` (built, Phase 5 M3), `partner`, `assistant` | Product surfaces the user opens from Collections / My World. Own their domain data; call platform APIs + publish events. |

**Why this is better than a flat module list:** GojoMessages (formerly My World) is not “another social feature” — it is the private network shell, and the 2026-08-02 re-spec makes that literal: its own graph, its own audiences and its own content (decision 4, Phase 2f). Seller chat is commerce, not World Chat. Co-watch Madeleine rooms sit on media + assistant. Dispatch is shared by travel and delivery and must be an explicit module, not an informal “shared engine.”

## 2b. Product vision → module map (the five pillars)

The GoJoGo vision is five interconnected pillars plus supporting systems. Nothing in it requires a new architecture — it requires **two structural decisions** and a handful of new/extended modules. Everything else lands inside modules that already exist.

One Cognito account powers everything, incl. GoJoAdmin later. |

Emergency contacts are `profile` — a fact about a person, not about a trip. **Decision 1 — a business is a profile.** The vision's universal journey ("create a Business Profile, build an audience, then activate commerce") means businesses must be discoverable, followable, content-publishing entities *before* any commerce exists. The cheapest correct model: `profile` gains `kind = PERSON | BUSINESS` plus business fields (category, address, hours, links) and an owning user. The entire social graph, feed, stories, watch, notifications, and search machinery then works for businesses with **zero changes** — a follow is a follow, a post is a post. The owner "acts as" the business on mutations (server-verified ownership, no second token). `partner` keeps owning the *operational* relationship (application, KYC, approval status); an approval flips the business profile's commerce state for its vertical. Do **not** build a parallel `business` module with its own graph — that forks every social feature forever.

**Decision 2 — the wallet is `payments`, and tokens/stakes are ledger rows.** Staking ($30 driver stake), the KYC fee deducted from it, ride-hailing token packs and per-ride deductions, verification rewards paid from a stake, tips, earnings, and refunds are all **internal balance transitions** — one double-entry ledger in the `payments` schema with buckets per user: `available`, `staking` (locked), `tokens`, `rewards`. Stripe (+ Connect) is the only thing that moves external money, and remains source of truth for charges; the ledger reconciles. "Token" is a ledger credit with a policy price — not a crypto asset, no chain, no speculation surface. A public `WalletApi` (credit/debit/hold/release with idempotency keys) is what `travel`, `delivery`, `economy`, `services`, and `partner` call; none of them ever touch Stripe directly.

**Decision 3 — identity is a vendor's answer, and the platform keeps only the verdict.** Proving a human is who they claim needs document-authenticity checks and a liveness match; a reviewer squinting at a phone photo of an ID card is not that, and the copies of everyone's passport it accumulates are a liability with no upside. So a platform **`kyc`** module owns the relationship with an IDV vendor (Sumsub) behind the `IdentityVerificationApi` SPECS §4 reserved, and the `kyc` schema stores a *decision* — status, reason, reject labels, the vendor's applicant id — and never the evidence. `partner` keeps the question a vendor cannot answer (should this **business** trade here), which stays a human approval. The interface is what makes the vendor swappable, and it is load-bearing in a second way: **unconfigured means the old path**, so an environment with no credentials still verifies by document upload and human review rather than being unable to onboard anyone. Every later pillar that needs a verified person — driver staking and payouts (Phase 3), sellers and providers (Phase 5) — reads the same API rather than growing its own check.

---

**Decision 4 — "My World" is now GojoMessages, and it is a private social network rather than a chat section.** Re-spec'd by the product doc of **2026-08-02** (`go2..pdf`), which opens by retiring the name: *"not my world anymore"*. What changes is not the label but the shape. The built product is a WhatsApp-style **chat** surface with a phone-verified identity bolted on; the spec describes a **second social network** — a graph built on phone numbers where **a username is never a way to find anybody** (amended 2026-08-02 — people are *added* by number only, but a contact still shows under their World `displayName`, and you can privately rename them; see Phase 2f), **circles** as the audience primitive (custom groups, one person in several), and its **own** posts, stories and carousels whose audience is "everyone who has my number" or "these circles". The public `social` feed stays exactly where it is; the doc confirms it ("now on gojogo we are to have the main feed"), so this is a split, not a replacement.

Three consequences worth stating before anything is built:

- **It settles an open boundary and reverses a decision's *reasoning* without reversing the decision.** Story replies were kept in `social` because "My World is a separate identity that will get its own stories" (§10, Phase 2c). That is now spec'd rather than anticipated — so the call stands, and the two content systems are genuinely two, not one with a flag.
- **The audience primitive is a graph this system does not have, and the content is therefore its own — resolved 2026-08-02.** `social` audiences are follow-based (plus close friends); GojoMessages audiences are *"has my phone number"* and *"is in this circle"*, neither of which is expressible in `social.follow`. The deciding question was whether a GojoMessages post can ever become a public one, and **the answer is no** — it is seen by contacts or by the selected circles and by nobody else, ever. So the two content systems are **genuinely two**, and the duplication is the point rather than a cost to optimise away. Folding them into `social` behind an audience flag would make every feed, profile, search and moderation read in that module responsible for a phone graph it cannot see, and **one missed `WHERE` clause would publish a private post to the world** — which is the failure this separation exists to make impossible. What is left open is only *which* module owns it (Phase 2f), never whether it is its own.
- **It reads like one account, and it is deliberately still two — decided 2026-08-02.** The doc has people signing up with Apple, Google **or a phone number**, and Apple/Google sign-ups later adding a verified number by 2FA, which reads as *one* phone-verified account. The call is to **keep the split**: a public app/social account (email/Google/Apple, `@handle`, public name and avatar) and a separate phone-verified **GojoMessages identity** with its own name and photo. It is the WhatsApp/Instagram distinction, and it is the one that fits a network whose whole premise is *"the people you actually know"* — the face you show forty acquaintances is not the face you show the internet, and collapsing them would take that choice away from everybody at once. Three built things keep working unchanged as a result: the story-reply boundary, `WorldContactView`'s optional "second hop" from a World identity to a public profile (confirmed as the right shape rather than a legacy artifact), and the separate World name shown in chat. Two consequences follow, and both are the reading this decision forces: **the doc's sign-up paragraph is *app* sign-up**, with GojoMessages keeping its own first-entry setup as it does today; and **the "username" collected at sign-up belongs to the public account**, which is exactly why the network itself needs no handle of its own — a handle is how the internet finds you, and a phone number is how your friends do. (It still has *names*: the World display name, and per the Phase 2f amendment a private per-viewer rename on top of it. What it has no use for is a globally unique lookup key.) It also means **the rich profile the doc describes — gender, current city, languages, education, occupation, interests, favourite books/films/TV/sport/games — belongs to the GojoMessages identity**, since that is the paragraph it appears in and the network where it makes sense. That is a real expansion: today the World profile is a name and an avatar in a DynamoDB item, and this turns it into a genuine profile with storage implications of its own. Still **blocked on SNS SMS** (PROGRESS "Needs YOU" #3) before any of it can be more than a plan. One built behaviour is contradicted outright either way: `addWorldContact` resolves an `@handle`, and the spec says **phone numbers only**.

The re-spec is written up as Phase 2f below, with what is settled separated from what is not.

## 3. Enforcing the boundary: Spring Modulith

Use **Spring Modulith** instead of folder-structure convention alone:

- Each domain is a top-level package (`com.gojogo.social`, `com.gojogo.profile`, `com.gojogo.media`, …). A module may expose a public API package; everything else is package-private.
- `ApplicationModules.of(GojogoApplication.class).verify()` fails the build if a module reaches into another module's internals.
- Cross-module communication:
  1. **Synchronous public API** — e.g. `ProfileLookupApi.getUser(id)`.
  2. **Asynchronous domain events** — e.g. `PostCreated`, `OrderPlaced`, `UserFollowed` via `@ApplicationModuleListener`. In-process now; SQS/EventBridge later is config, not a rewrite.
- `@ApplicationModuleTest` boots one module in isolation — extraction stays low-risk.

**Live packages today:** `com.gojogo.auth` (incl. the platform-admin principal and Cognito account admin), `profile` (incl. business profiles, act-as resolution, `/v1/auth/session` and account deletion), `social` (incl. blocking), `media`, `music`, `messaging`, `notifications`, `economy`, `delivery`, `watch`, `partner`, `kyc`, `payments`, `config`, `storefront`, `moderation`, `dispatch`, `travel`, `share` (plus app-level `SecurityConfig` / `ApiExceptionHandler`). `notifications` is the busiest cross-module event consumer (`social`'s `UserFollowed` / `PostLiked` / `PostCommented` / `StoryReacted` / `StoryReplied`, `messaging`'s `MessageSent` for chat push, and `partner`'s `PartnerReviewed` for an approval or rejection). `economy` publishes `ListingCreated` (still no consumer — search is a later slice), `delivery` publishes `OrderPlaced` (likewise) and `OrderStatusChanged` (**consumed since 2e M3**), and `payments` publishes `MoneyReceived` / `PayoutSent`, both consumed by `notifications`.

**Three module edges arrived with Phase 4 M2 and none of them is new machinery.** `delivery → messaging` (the courier↔customer thread, the third consumer of the `ConversationContext` seam after a listing and a ride — which is the return on having made it generic in 2b M3), `delivery → media` (`MediaDocumentApi`, because a photo of somebody's front door belongs in the private prefix beside a KYC paper and nowhere near the world-readable one), and `dispatch → payments` (`WalletApi`/`PayoutApi` for the worker payout surface — platform→platform, and no cycle, because `payments` has never heard of `dispatch`).

**Public cross-module APIs in use:** `ProfileApi` (now also `requireActingProfile` — the one server-side ownership check behind acting as a business — plus `businessesOwnedBy` / `findBusiness` / `setBusinessVerified`), `MediaApi` + `MediaDocumentApi`, `MusicApi`, `MessagingApi` (+ `ConversationContext`), `SocialGraphApi`, `MerchantProvisioningApi`, `IdentityVerificationApi` (the IDV seam — see §2b), and `WalletApi` / `FeeApi` / `PayoutApi` / `TokenApi` (the money seam: a vertical asks for a movement in minor units — or, for tokens, in whole tokens — and never learns that Stripe exists, nor what a token is worth), `ConfigApi` (effective-dated policy values, read with a compiled-in default so an empty table behaves like a populated one), `StorefrontApi`, and — 2e M5 — `PlatformAdminApi` / `AccountAdminApi` in `auth`, plus an extended `SocialGraphApi` (`blockedIds` / `blockedBetween`).

**Four seams run the other way, and it is deliberate** (2e M5, extended by 3 M4 and 3 M5). `messaging.ConversationGuard`, `moderation.ModeratableContent`, `dispatch.WorkerEligibility` and `share.ShareableResource` are interfaces a *platform* module defines and a *vertical* implements — the platform collects whatever implementations exist and calls them. It exists because blocking must live beside the follow graph it tears down and only `social` knows what a post is; because only `travel` knows what a ride costs a driver in tokens, and `dispatch` must no more learn about a token than about a fare; because only `travel` knows where a car is *right now*, and a public link that resolved to a stored position would be a screenshot; and because asking a vertical for permission the other way round would make a platform module depend on one, which is the direction §2 forbids and the thing that makes a module extractable. A platform module with no implementations on the classpath behaves exactly as it did before the interface existed. Each is deliberately narrow — a consumer gets the one verb it needs, never the module's model. Where a vertical needs to *change* something another module owns (following, a chat, a catalog entry), it either sends the user to that module's own surface or asks for exactly one operation and gets an id back.

## 4. Data ownership rule

**Schema-per-module in one physical Postgres database:**

- Platform/vertical schemas as modules land: `profile.*`, `social.*`, `media.*`, `messaging.*` (Postgres side where needed), `notifications.*`, `economy.*`, `delivery.*`, `travel.*`, `partner.*`, `dispatch.*` (or Redis-primary with a thin Postgres ledger), `services.*`, `payments.*` (the GoJo Wallet double-entry ledger — live; Stripe is source of truth for external charges and is reconciled against it), `platform.*` (the config registry — live), `kyc.*` (identity **verdicts** only — the documents live with the IDV vendor, deliberately not here).
- **No foreign keys across schemas. No cross-schema JOINs in application code.** Cross-domain reads go through public APIs or events.
- Messaging / live position / Madeleine memory may use **DynamoDB** where write patterns demand it; that does not excuse mixing Postgres ownership across modules.

This is the highest-leverage rule in the document: extraction later is a connection-string change, not a data model rewrite.

## 7. iOS client architecture

The backend modules only matter if the client stays aligned.

### Current shape (Phase 1)

| Piece | Role |

A full split of `AppState` into many `@Published` stores was **deferred** (views are tightly coupled). Revisit when the next domain goes live — add a store, keep `AppState` as the façade until a vertical is mostly API-backed.

### Navigation (must stay in sync with backend product splits)

- `AppNavMode`: `.myWorld` (private network) vs `.collections` (public superapp tabs).

- Auth: `AuthPhase` `.welcome` → `.email` → `.onboarding` → `.app`.
- Travel: `TravelPhase` home → searching → choosingRide → matching → enRoute → inTrip → completed.

### Rules

- Drive UI from `AppState` (or thin stores behind it) — no parallel global navigation stacks.
- Live path: optimistic UI → API; DEBUG log failures; keychain session restore on launch.
- Do not invent a second networking stack; extend `APIClient` / stores per module.

First cross-vertical use of a platform module's public API; the boundary is enforced by `ModularityTests`. **M1 deployed + verified (2026-07-23):** the `economy` vertical module (listings CRUD, browse/keyset pagination, save/unsave, mine/saved) + iOS wiring (`EconomyStore` / `AppState+Economy`, live catalog + sell-with-photo) are live in prod; publishes `ListingCreated`; two-user curl E2E green. ### Phase 2c — Stories, properly

- `social` stories go from a stub (one image URL, 24h, seen flag) to the whole product: photo / video / text-card frames with a client-authored overlay spec, replies, reactions, a viewers list, mute, archive, highlights, and a close-friends audience. Four migrations (`V11`–`V14`), no new module and no new AWS infra — it reuses `media` presign and publishes two new events (`StoryReacted`, `StoryReplied`) that `notifications` consumes.
- **Music is a platform module, not a story feature.** `music` owns the shared track catalog (`music` schema) and exposes `MusicApi`; `social` resolves a track through it and then stores its **own snapshot** on the frame — no FK across schemas, and a story keeps playing the sound it shipped with after a track is pulled. Shorts and posts are the obvious next consumers. The catalog ships empty and has no ingest endpoint by design (there is no admin role); seeding it is a licensing decision — see PROGRESS.md "Seeding the music catalog".
- **Story replies stay in `social`, not `messaging`.** This is the one boundary call worth writing down: GojoMessages is a separate, phone-verified identity that will get its **own** stories — **spec'd rather than merely anticipated since 2026-08-02** (decision 4), which is what turns this from a guess into a rule — so routing a reply to a *social* story into a My World DM would cross two identities the app deliberately keeps apart. Seller chat goes through `MessagingApi` because a marketplace conversation genuinely is a conversation; a story reply is a private comment on a piece of content, and it belongs to the module that owns the content. See PROGRESS.md "Phase 2c".
- OpenSearch consumer for `PostCreated` / `ProductCreated`.
- `partner`: onboarding + KYC document upload. **Built + verified 2026-07-27 (not yet deployed), shipped as Phase 2b M6** — pulled forward out of 2c because it was the blocker for `delivery` being usable at all: the demo catalog was deleted, and the only way a restaurant could exist was a Flyway migration. The module owns the *business relationship* (an application, its KYC documents, and a status a human moves), and is generic by design — `kind` is `RESTAURANT | DRIVER | COURIER`, since a driver's application is the same object with somewhere else to land. On approval it **provisions into a vertical** through that vertical's public API: today only `delivery.MerchantProvisioningApi`, which returns the merchant id; `DRIVER`/`COURIER` are refused at approval time until Phase 3 `dispatch` exists, rather than approved into nothing. The dependency is one-way (`partner → delivery`) and the only trace left in delivery is an `owner_id` on the merchant row — which is the entire basis for its owner-scoped `/v1/delivery/merchants/mine` catalog surface, so delivery never learns that KYC exists. **Two boundary calls worth recording:** approval is a *human* act on a token-guarded surface outside the JWT chain (this app has no admin role — the same constraint that left the music catalog without an ingest endpoint), and **KYC documents are not `media`'s public product**. Everything `/v1/media/presign` mints lands under a world-readable prefix, so `media` gained a second public API, `MediaDocumentApi`, that presigns into a private prefix and hands a reviewer a short-lived signed GET; consumers store object keys, never URLs. **Restaurants are created in Gojo Admin, not in the app** (decided 2026-07-27). The applicant-facing iOS flow was removed; the module and its endpoints are unchanged, and the operator drives the same application → KYC → review → provision path from the admin tool. iOS keeps only the **merchant dashboard** — an owner running their own storefront and menu — gated by `AppState.merchantDashboardEnabled` pending a call on whether that moves to admin too. The one thing this implies and doesn't yet have: an **admin-side create**, since the applicant endpoints are caller-scoped. See PROGRESS.md "Phase 2b · Milestone 6".

This is the highest-leverage phase in the vision plan — every later pillar (transport staking, delivery payment, commerce checkout, services booking) blocks on the wallet, and every economic player's journey starts with a business profile.

Deviations worth recording: act-as also covers likes/follows server-side (the app uses creation only, since reads are decorated for the caller), and `maxBusinessesPerOwner` is a constant until the config registry lands in M3. Followable/discoverable/content-publishing immediately, because a business *is* a profile (§2b decision 1). Built + deployed 2026-07-30** — `platform-admin` Cognito group read from `cognito:groups`, `POST /v1/partner/admin/applications` (owner by id or handle, reusing the merchant's own write path), admin submit + document verbs + a per-document signed link, `isPlatformAdmin` on `/v1/me/roles`, and a `WEB_ALLOWED_ORIGINS` CORS allowlist. Original plan text follows. - **M3 — Payments + GoJo Wallet. Built + deployed 2026-07-31** — `V22`–`V25`, the `payments` and `config` modules, delivery checkout, and the `OrderStatusChanged` consumer. Deviations worth recording: **card money always arrives as a wallet top-up** (a hosted Checkout session) rather than as a per-order card charge, so a vertical only ever has one payment path to integrate and no card data exists in this system; **the courier's delivery fee and tip settle to `PLATFORM` under their own ledger kinds** until Phase 4 M1 creates couriers, rather than being folded into commission; **a promotion is always funded by the merchant**, free-delivery included, which is what keeps a discount from ever reducing what the courier is paid; and **merchant balances and payouts live on `delivery`'s `/mine` surface**, not on payments' own — only the vertical that owns a payee can prove the caller owns it, and the reverse dependency would be a cycle. ### Phase 2f — GojoMessages (the My World re-spec)

**Re-spec'd 2026-08-02 from the product doc; M1 and M2 built the same day. The phase is code-complete and undeployed.** Decision 4 has the shape and the reasoning; M1 and M2 below are the work it implied. The four questions this section opened are all now closed — see them struck through further down. What is *not* closed is **SNS SMS** (PROGRESS "Needs YOU" #3): the graph is built and works against the dev bypass code, but nobody outside a verified test number can join it in production until that clears, so this phase ships to a locked door.

- **M1 — Name, lookup and private renames. Built 2026-08-02 (not deployed).** The three pieces that needed no phone graph and therefore no SMS: the **product rename** in every user-visible string (the wire, the DynamoDB prefixes and the iOS type names deliberately unchanged); **`addWorldContact`'s `@handle` lookup deleted**, along with `startLiveConversation(handle:)` and the handle branch of `startLiveGroup`, so a thread starts from a number and only from a number; and the **per-viewer contact alias** end to end — a new `ALIAS#` item under the viewer's own `WORLDUSER#` partition, `GET`/`PUT /v1/world/aliases`, a client lens in `MessagingStore.map`, a rename affordance on `WorldContactView`, and per-recipient push titles. **No migration**: `messaging` is DynamoDB-only, which is also why this slice could be built alongside Phase 4 M1's `V35` without either touching the other. `ModularityTests` green; iOS builds. **Not built, and not startable yet:** circles server-side, GojoMessages content, the rich profile, the feed home screen. See PROGRESS.md "Phase 2f · Milestone 1".

**What the doc settles:**

- **The name.** "My World" → **GojoMessages**, everywhere a person can see it. The wire (`/v1/world/**`), the DynamoDB item prefixes (`WORLDUSER#`, `WORLDPHONE#`) and the iOS type names (`WorldSocket`, `MyWorldView`, `WorldPreference`) are a separate, cheaper decision — renaming a live URL costs a client release and buys nothing, so the sane split is *product name now, identifiers whenever a file is being edited anyway*.
- **The graph is phone numbers, and only phone numbers — but that is a rule about *lookup*, not about names (amended 2026-08-02).** People are **added** by number and only by number: `addWorldContact`'s `@handle` lookup is spec'd out of existence. What is *not* removed is the name — a contact still shows as their **World `displayName`**, the name they set in GojoMessages setup, exactly as `MessagingService.worldName` already renders it. The earlier reading of the doc ("usernames do not appear in this network at all") was too strong: it correctly killed the public `@handle` as a *way to find somebody*, and wrongly took the person's name with it. The public `@handle` still never surfaces as a label here — that part stands, and it is what keeps decision 4's two identities apart.
- **A contact can be renamed, and the rename is yours alone (added 2026-08-02).** Any contact carries a **per-viewer alias**: I rename someone in GojoMessages to whatever I want, and that is what I see everywhere their name appears. It does **not** change the name they set, it is **not** visible to them, and it is not visible to anyone else — it is a property of the *edge* from me to them, not of them. The WhatsApp address-book rename, except the address book is server-side here. Three consequences fall out of the code as it stands:
  - **It belongs to `messaging`, account-level, not device-local.** The contacts graph is already server-side, and an alias is about a *person*, not about this handset — so it does not go in `WorldPreference` next to the mutes and wallpapers, which are device-scoped **by design**. Renaming on the phone should show up on the iPad.
  - **Resolution is a client-side lens, not a server read-time rewrite — corrected in build, 2026-08-02.** The plan above said `toConversationDto` / `toMessageDto` should apply the alias on the way out. Building it showed that is wrong, for a reason worth keeping: **the WebSocket fan-out publishes one `MessageDto` to every participant at once.** A name resolved server-side would therefore be right over REST and wrong over the socket — the exact inconsistency the feature exists to avoid. So **the wire always carries real names and ids**, and the client applies its own renames at the point where DTOs become app models. One lens, in `MessagingStore.map`, and every surface that renders a name inherits it.
  - **The server resolves per-viewer in exactly one place: push.** A device can't rewrite an APNs alert after delivery, so a push is the one name the server renders *on a specific viewer's behalf*. `MessageSent` carries a `senderNameByRecipient` map, and `notifyRecipients` fills it with a targeted alias lookup per recipient. Everywhere else, per-viewer server rendering would mean fanning out N payloads to save the client a dictionary lookup.
  - **Quoted replies needed an id, not a de-stamping.** `buildReply` stores `authorName` into the message row — one string every viewer reads — so the plan was to stop storing it and resolve from `senderId` at read. Adding **`authorId` to `ReplySnippetDto`** turned out to be the smaller fix with the same outcome: the client aliases the quote by id, and the stored name stays as the fallback for snippets written before the field existed (Jackson decodes the absent field as null). Without this the alias would have been right in the bubble and wrong in the quote directly above it.
- **Circles are the audience primitive.** Custom groups of contacts, one person in as many as you like. Were UI-only for the whole of Phase 2; **built server-side in M2**, where a circle also refuses any member who isn't already a contact.
- **GojoMessages owns content**: posts, stories and carousels, published to *everyone you have added* or to *named circles*. **Corrected 2026-08-02** from "everyone who has your number": that direction handed the audience to the wrong person — anybody holding your number could add you and start receiving everything you posted, and you had no way to remove them. An audience the author cannot close is not an audience. This is the substantial half of the milestone and the part with no existing home.
- **The home screen is a feed, not a conversation list** — stories row, then posts from people whose number you have, then the messages list underneath.
- **The chat detail screen does not change.** Stated explicitly, and worth honouring: it is the one part of this product that is finished.
- **A contact's profile gains a shared-content tab** — info, backgrounds, photos, links, documents, and then everything that person has published to their phone graph or to a circle you are in. `WorldContactView` already renders the first four off the thread; the last one needs the content system.
- **The profile grows a lot**: bio, gender, current city, languages, education *from a worldwide schools database*, occupation, interests, hobbies, favourite books / films / TV / sport / games. `profile` has four of those today. The schools database is an external dependency nobody has chosen — a vendor, a dataset, or a free-text field with autocomplete added later.

**What the doc does not settle, and should before code:**

1. ~~**One account or two?**~~ — **decided 2026-08-02: two.** The public app/social account and the phone-verified GojoMessages identity stay separate (decision 4). So the doc's sign-up paragraph is *app* sign-up; GojoMessages keeps the first-entry setup it already has; the `@handle` collected at sign-up is the public one, which is precisely why the private network needs none. What this **does** add is the rich profile — gender, current city, languages, education, occupation, interests, favourite books/films/TV/sport/games — onto the **GojoMessages identity**, which today is a name and an avatar in a DynamoDB item. Turning that into a real profile is its own piece of work, and the storage question (stay in the `messaging` DynamoDB table, or move to Postgres now that it has structure worth querying) is open.
2. ~~**Who owns GojoMessages content?**~~ — **half-answered 2026-08-02: never `social`.** A GojoMessages post is seen by the author's contacts or by the circles they picked, and by nobody else — it **can never become public**. That is what makes the two content systems genuinely two rather than one with a flag, and the duplication is the point rather than a cost to optimise away: folding them into `social` behind an audience column would make every feed, profile grid, search, archive, highlight and moderation read in that module responsible for a phone graph it cannot see, and **one missed filter would publish somebody's private post to the world** — the worst bug this codebase could ship, and the one this separation exists to make impossible. What is still open is only *which* module owns it:
   - **Extend `messaging`** — it already owns the phone identity, the contacts and (once built) the circles, so the content sits next to the graph that authorises reading it. The precedent is blocking, which lives in `social` beside the follow graph it has to tear down in the same transaction: an audience check that spans two modules is one deploy away from disagreeing with itself.
   - **A new module that depends on `messaging`** for the graph and owns only the content. The argument for it is §2: `messaging` is a *platform* module, and a social network's content is product surface, which is a line this would blur.
   - Either way **circles have to move server-side** — they are UI-only today and cannot be an audience while they exist only on a phone.
   - **Fully answered 2026-08-02 (M2): `messaging` is extended.** The deciding argument is the one already written above — an audience check is a *graph* question, and splitting the content from the graph puts the only thing standing between a private post and the world across a module boundary. The blocking precedent settles it: that lives in `social` beside the follow graph it must tear down in the same transaction, for exactly this reason. The §2 objection is real and is accepted as a cost rather than dismissed: `messaging` is a platform module now carrying product surface, and the mitigation is that content never leaves through `MessagingApi` — no vertical can reach it, so the blur is internal to the module rather than visible in the dependency graph. **Circles duly moved server-side**, and a circle is refused any member who isn't already a contact, so publishing to one cannot reach outside the graph.
3. ~~**Do the two networks share stories?**~~ — **decided 2026-08-02: no, two systems and two composers.** The doc's third mockup does put a stories row on the Gojogo main feed, but making one story object serve both audiences would reintroduce precisely the failure decision 4 exists to prevent: a single row whose reach depends on a flag, one missed filter away from publishing a private story publicly. So `social`'s stories (and their archive and highlights from 2c) are untouched and keep their own composer, and GojoMessages stories are separate objects with a 24-hour TTL of their own. The cost is a second composer and no cross-posting; that is the intended cost.
4. ~~**What is the worldwide schools database?**~~ — **decided 2026-08-02: free text, no vendor.** Education is a plain field on the rich profile. An autocomplete can be layered onto the same field later without migrating anything, and licensing a dataset before a single person has typed a school name is paying for a feature nobody has asked for yet.

**The one thing that was cheap and worth doing first, whatever was decided:** the rename in the product surface, and deleting the `@handle` path from contact-adding. Both were small, both unambiguous in the doc, and neither waited on SMS — they shipped as M1.

- **M2 — The private network itself. Built 2026-08-02 (not deployed).** Everything the re-spec asks for on top of M1: a **server-side contacts graph** (an edge plus a reverse edge written in one transaction, which is what makes "everyone who has my number" answerable at all), **circles as a real audience**, **posts / stories / carousels owned by GojoMessages**, the **rich profile**, and the **feed home screen** with its composer, story viewer, circles manager and contact shared-content tab. Still **no migration** — all of it is DynamoDB in the existing table, which kept it clear of Phase 4 M1's `V35`. Deviations worth recording: **content is fanned out on write** to exactly the resolved audience, so a reader only ever queries their own partition and there is no audience filter on the read path that could be forgotten — the cost is writes proportional to audience size, which is the right trade for a network of people you actually know; **"what has this person published" is answered from the *viewer's* partition**, filtered by author, rather than from the author's, because the two give the same answer on a good day and only one of them can leak; **the audience is stripped from every reader's copy**, so nobody learns which of an author's circles they landed in; **dropping a contact removes them from every circle in the same call**, since a stale circle is a stale audience; and **a contact's rich profile is returned only to an actual contact** — knowing a number is how you reach someone, not a licence to read where they went to school. `WorldAudience` has two constants and a test that fails the build if a third appears. **Not built:** SMS-gated real phone verification (still "Needs YOU" #3), post reactions/comments, and a GojoMessages story archive. See PROGRESS.md "Phase 2f · Milestone 2".

- **M1 — Real couriers. Built and deployed 2026-08-02** — `V35`, a merchant order queue, a courier job surface, `OrderFulfilmentJob` and `DeliveryTimeline` deleted, and the courier finally paid. Deviations worth recording: **the kitchen had to become a person before the courier could** — deleting the job removes the only thing that ever moved an order, so a merchant queue (accept with a prep estimate / reject / ready) is what "delete the simulation" costs, not scope creep; **`readyAt − pickupLead` is `DispatchRequest.startAfter`**, the field M1 built for this and no caller had ever used, so "approaching readiness" needed no new mechanism; **no seventh status** — "cooking, and nobody has taken the delivery" is a `courier_search` column beside the status, because that is a problem with an order rather than a stage of one, and a new status is a word every client in the field has to learn; **an exhausted search is flagged, not retried and not cancelled** — dispatch's job row is unique per (kind, ref) by design, re-asking is the same question to the same empty city, and auto-cancelling would throw away food that may already be made; **a restaurant that never answers is a real failure now**, so `OrderTimeoutJob` cancels and releases after ten minutes and collects the orders this deploy stranded by the same test; **the courier's own REST surface is two verbs** (collected, handed over) because availability, position, offers and accept are dispatch's and identical for a driver; and **the order rating is not fed to `dispatch.complete`** — a two-star for a cold burger is about the food, and must not land on the record of whoever cycled it across town. **Not built:** a courier rating of their own, handoff codes and PINs (M2), a courier-side share link, and a second courier search for an order nobody took. See PROGRESS.md "Phase 4 · Milestone 1". Original plan text follows. `partner` COURIER approvals provision into `dispatch`; the simulated `OrderFulfilmentJob` is deleted and dispatch assignment drives the same state machine and `OrderStatusChanged` events — the swap 2b M4 was explicitly designed for. Courier *pay* is already separated out: 2e M3 settles the delivery fee and the tip to `PLATFORM` under the `COURIER_FEE` / `TIP` ledger kinds, so this milestone changes a payee and nothing else. Courier Mode: availability, offers, live navigation, earnings via wallet.
- **M2 — Handoff integrity + money. Built 2026-08-02** — `V38`, a pickup code and a delivery PIN, contactless proof photos, the courier↔customer thread, and a worker payout surface in `dispatch`. M1 made the courier a real person and left the two moments that matter most **unwitnessed**: a courier taps "I have the food" and the order moves, taps "I handed it over" and the money moves. This milestone is the evidence behind those two taps. Deviations worth carrying forward. **The code direction is reversed from SPECS §5** — the merchant's screen displays the pickup code and the *courier* types it, not the other way round, because the party who must act should be the party with the incentive: a busy merchant who forgets to tap strands a courier holding food they cannot mark collected, while a courier cannot be paid until they finish the step and can only learn the code by standing at that counter, which is the fact the code exists to prove. **A wrong code is a 200, not an error** — both verbs return a result object with the attempts left, because a courier who typed a 7 for a 1 has not made a bad request, and mechanically it is what lets the attempt counter commit instead of being rolled back by a thrown exception. **Attempts are counted at the door and deliberately not at the counter**: at the counter the merchant is standing right there so the code is a check rather than a gate, and locking a courier out of food they are already holding is the worse failure; at the door the risk runs the other way. **An empty PIN counts as a wrong attempt**, which is what makes three taps the honest way out of a doorstep nobody is answering. **The fallback after lockout is a deliberate, documented hole** — it can be abused, and a courier stranded in the street with somebody's dinner is worse; the attempts are recorded and never reset, and the photo is the evidence. **Still no new order status** (SPECS §5 says a failed PIN leaves an order `ARRIVED`; there is no such status and M2 did not add one — a failed handoff leaves it `DELIVERING`, which is what it is). And **the worker payout surface is `dispatch`'s, not `delivery`'s** — one surface for drivers and couriers, since a dual-mode person has one balance and dispatch owns the registry that proves the caller is somebody the platform pays for work; `PayoutApi`'s own javadoc has named dispatch for this since 2e M3. It carries the milestone's other real decision: **a worker is paid into their own `USER AVAILABLE` bucket, the same pocket a card top-up lands in**, so a payout over a raw balance would be this platform's first card→bank path, and the withdrawal is capped at `min(available, earned − already paid out)` (SPECS §1). **Not built:** a courier rating (still), pickup QR *scanning* (the code is rendered as one; typing is the path), disputes (SPECS §5, still Phase 4's own later slice), and a share link for a delivery. Original plan text follows. Pickup verification (QR/order code at the merchant), delivery confirmation (PIN / photo / contactless), tips through the wallet, courier earnings + withdrawal. Courier↔customer contact = `messaging` thread with `ConversationContext(kind=ORDER)`.
- **M3 — Multi-merchant orders. Built 2026-08-04** — `V40`, `delivery.sub_order`, one checkout across kitchens and a courier who proves every counter. The prediction M2 left behind held: **the pickup code moved down to the sub-order** exactly as SPECS §5 said it would, and that was the milestone's spine rather than an afterthought. Deviations and decisions worth carrying forward. **The parent keeps the six statuses and the courier; the sub-order gets a fifth word of its own, `COLLECTED`** — "this kitchen's bag is in the courier's hand" is a fact about one merchant, and the parent only reaches DELIVERING when the last bag is. No seventh order status, for the third milestone running. **The courier search waits for every kitchen to answer and is timed to the slowest** — `max(readyAt) − pickupLead`, still `DispatchRequest.startAfter` and still no mechanism of delivery's own; a search opened on the fast kitchen's clock is a courier standing at a counter waiting for the slow one. A **rejection counts as an answer**, so a kitchen saying no releases the search rather than stalling it forever. **Cancellation is per sub-order until its merchant accepts** (SPECS §5), with a partial escrow release of exactly that slice's share — `subtotal − discount + its delivery fee`; the service fee and the tip are the order's and only move at the end. `released_cents` on the parent is what keeps settlement honest: **splits + released must equal the hold**, the same invariant as before with a second term, and the last live slice cancelling ends the order in one movement rather than a share plus a rump. **A promotion is resolved per kitchen**, because a promotion is one merchant's own campaign — a checkout-level code is tried against every basket and applied where it lands, and refused out loud only when it lands nowhere. **The multi-courier per-leg split is deliberately not built**; what makes that honest is the cap — `delivery.order.max.merchants` (CONFIG 3), because three counters is a trip one person makes and five is a relay. **Wire compatibility is total**: the legacy `merchantId + lines` checkout still places, `OrderDto` keeps every flat field (the first slice's merchant, all the lines) beside the new `subOrders`, the kitchen's queue DTO is unchanged in shape with the id now naming a sub-order, and the courier's job carries `stops` beside a `merchantName` that points at the next uncollected counter. **`OrderPlaced` is published once per kitchen** — each owner is told about their slice and its own food value, not the whole checkout. `SUB_CANCELLED` is a push-only status word that is not one of the six and that older clients drop on the floor. **Not built:** disputes (SPECS §5, still Phase 4's own later slice), a courier rating (still), and a share link for a delivery. See PROGRESS.md "Phase 4 · Milestone 3". Original plan text follows. One checkout, one payment, sub-orders per merchant (each with its own preparation/fulfilment state), dispatch coordinating pickups/couriers, per-sub-order tracking. The unified-cart UX rides on the existing server-priced order model — sub-orders are the only schema change.
- **M6 — Disputes, and the rest of the breadth. Built 2026-08-05 — this closes Phase 4** — `V43`, `delivery.dispute` (+ items and photos), a courier rating, recipient orders, `delivery` implementing `share.ShareableResource`, and opening hours. Deviations and decisions worth carrying forward. **A dispute is argued after the money has moved**, so there is no pot to refund from: a refund is money coming back off somebody already paid, and the only answerable question is *which of the three* — kitchen (food less commission), courier (fees and tip), or platform (commission and service fee). Each is **capped at what they actually received for this order**, because taking one order's dispute out of another order's earnings is how a restaurant finds a refund it was never shown. **None of them can go below zero** (only EXTERNAL accounts may), so a merchant who has withdrawn cannot fund one — a 409 naming the number, never a silent fallback to the platform, because deciding who absorbs it on somebody's behalf is how the platform pays for every kitchen's mistakes without anybody choosing that. **Resolution is a human act and the code keeps it one**: no auto-refund, no timer, no scoring, and a `resolved_by` no rule could fill in. **One dispute per order** as a unique index — per-kitchen reads better until two operators refund the same missing pizza twice. **The claim is ids and quantities, never an amount.** `DISPUTE_RESOLVED` is the third push-only word and carries **no amount**, because the alternative was money in a field called `etaMinutes`. **The courier rating goes to `DispatchApi.rate`, not `complete`** — the job ended at the doorstep, and re-completing would count it twice; it is a second question beside the order rating, which is the M1 reasoning honoured rather than reversed. **A recipient's name reaches the courier and their phone reaches nobody.** **`delivery` is the second implementation of `ShareableResource`** and cost `share` nothing, as 3 M5 predicted. **Opening hours are checked at checkout for an immediate order and at promotion for a booking**, since a kitchen shut at lunchtime may be open at eight; stored as one column in the restaurant's own timezone, overnight as a normal case. Two bugs found building it: the parser asked `DayOfWeek.valueOf("WED")` (the enum spells it `WEDNESDAY`) so **every schedule failed open silently** — it now logs; and the check exposed that **checkout never verified `active`/`suspended` at all**. **Category expansion was already there**: `merchant_category` since `V8`, browse filters on it, so grocery/pharmacy/retail are data rather than a build. **Not built:** package delivery (an order with no merchant catalog — it breaks `sub_order.merchant_id`, per-merchant settlement and the counter handoff, and is a milestone rather than a slice), errands (SPECS §15), recurring orders, and any way for a merchant to contest a dispute. See PROGRESS.md "Phase 4 · Milestone 6".
- **M5 — Scheduled orders + changing one before a kitchen sees it. Built 2026-08-05** — `V42`, `customer_order.scheduled_for` / `queue_at` / `queued_at` / `revision`, a `ScheduledOrderJob` that promotes a booking when its moment comes, and `PUT /v1/delivery/orders/{id}`. M4's breadth work taken as its second slice; M4 predicted the cheap half ("a scheduled pickup is the same poller with no `pickupLead`") and that is about a fifth of it, because the timing was never the difficulty — **an order can now exist for six hours before anybody is asked about it**, and everything below follows from that. Deviations and decisions worth carrying forward. **The money is held at checkout, not at promotion**: a hold taken at 19:10 for a 20:00 dinner can fail at the one moment nothing can be done about it, so money reserved early is what the promise costs. **No seventh status, for the fifth milestone running** — CONFIRMED already means "placed, waiting for the restaurant to answer", which is exactly what a booking is; what differs is `queued_at`, and its null carries two load-bearing facts (no kitchen has seen it, so it is still the customer's to rewrite; and nobody has been asked, so the accept timeout has nothing to count — measured from `placedAt` it would cancel tomorrow's lunch ten minutes after it was ordered). **The kitchen is told at promotion**, which moved `OrderPlaced` out of checkout into one `announce` shared by both paths: the event exists to put an order in front of a person, and a push at noon about an eight o'clock dinner is a push somebody will have forgotten. **A prep estimate answers "how long do I need", not "when do I start"** — `readyAt = max(now + prep, the booking's target)`, `max` rather than the target so a kitchen that needs longer slips the promise visibly instead of the system promising on their behalf. **`queue_at` is computed once at placement** from the slowest kitchen's advertised time plus the accept window, so a merchant editing their ETA cannot move an order already promised to somebody; the same arithmetic refuses a time nobody could cook for, stated as *an amount of notice* rather than a time of day (the server does not know the customer's timezone) with the exact instant riding on the quote as `earliestScheduleAt`. **A booking does not occupy the one-live-order slot**, and a promotion landing beside a live order is accepted rather than deferred — `ActiveOrderResponse` grows `orders` and `scheduled` beside the flat `order`, which keeps carrying the soonest-arriving one. **A change is the order placed again**: the same body on a `PUT`, re-priced from the menu, everything replaced rather than patched, and the hold moved by the *difference* with the revision in the idempotency key — a release plus a re-hold would read as a refund and a second charge for an order that never stopped existing. The window is exactly "no kitchen has been told", which is the vision's "before preparation begins" read literally. **A restaurant that has closed since is cancelled at promotion** rather than left to fail an accept timeout ten minutes later. Dispatch did not change by a line, for the fourth milestone running. **Not built:** turning a booking into an immediate order (cancel and reorder), recurring orders, per-slice rescheduling, and **opening hours**, which this vertical still does not model at all — a booking for 3am is accepted and times out unanswered, which is honest but is the obvious next gap here. See PROGRESS.md "Phase 4 · Milestone 5".
- **M4 — Breadth. Pickup / collect-in-store built 2026-08-04** — `V41`, `customer_order.fulfilment_kind`, `merchant.pickup_enabled` / `pickup_prep_minutes` / `pickup_address`, and a collection handoff that is the M2 code read the other way round. The gap SPECS §5 recorded on 2026-07-31 — the vision, this plan and §9's `info` block all assumed collection existed and none of them defined it. Deviations and decisions worth carrying forward. **It is a fulfilment kind and not a delivery with a zero courier**, which sounds like a modelling nicety and is the whole milestone: the zero-courier version needs a null courier in every screen, a zero fee on every receipt and a job dispatch must never be offered, each special-cased where it lands, while a kind is one branch taken at three places — pricing, the courier search (`maybeOpenCourierSearch` returns on one line), and who types the code. **The kind belongs to the order, not to the sub-order**, and this is the one place the milestone departs from what M3 predicted. Per-merchant reads well until the money is followed: a mixed order needs a courier for some bags and not others and then has to decide whether the parent is finished when the courier is done or when the customer eventually walks to the other counter — with one hold, one settlement and one terminal moment to answer that with. A checkout is one kind; a cart whose kitchens do not all offer collection is refused at the kitchen that cannot, by name. What M3's per-slice code still buys is real — a customer collecting from two kitchens proves each counter, exactly as a courier does. **The code direction inverts, and it is one rule rather than two exceptions**: M2 reversed §5 for a delivery because the courier is the party who cannot be paid until the step is done; on a collection the payee is behind the counter, so the customer shows and the kitchen types — which is what §5 asked for. Underneath both: *the code is displayed to the party that does not type it, and typed by the party who is paid for completing the step.* Mechanically that means `MerchantOrderDto.pickupCode` is blank on a pickup slice while `SubOrderDto.collectionCode` is populated. **A wrong code is a 200 that says so and is never counted** — M2's counter-versus-doorstep asymmetry applied at the same kind of counter it was written for. **Readiness becomes a fact beside the estimate**: `ready_marked_at` does not overwrite `ready_at`, because for a collection the estimate is when to set off and the mark is "it is on the counter"; it drives **`READY_FOR_PICKUP`**, a push-only word that is not one of the six, the same shape as M3's `SUB_CANCELLED` — **no seventh status, for the fourth milestone running**. **The money needed no new arithmetic**: no delivery fee, no tip, and `settle` builds the same splits with the courier's two at zero, which the ledger drops because a zero fee is not an entry — so a collection pays food − commission to the kitchen and commission + service fee to the platform. A `FREE_DELIVERY` promotion is refused by name rather than left to return zero, because that zero is an accident of the fee being zero and the day it becomes a flat amount it would silently be money off food. **Not built:** the rest of M4's breadth — scheduled orders (now cheap: a scheduled pickup is the same poller without `pickupLead`), modify/cancel before preparation, order-for-someone-else, category expansion — plus disputes and a courier rating, and a sweep for a collection nobody comes for. See PROGRESS.md "Phase 4 · Milestone 4". Original plan text follows. **Pickup / collect-in-store first** (SPECS §5 — a gap found 2026-07-31: the vision, this plan and the storefront `info` block all assumed it existed and none of them defined it). It is an order `fulfilment_kind`, not a delivery with a zero courier: no dispatch, no courier states, no delivery fee or tip, and the existing handoff code shown to the customer instead of the courier — which makes it the cheapest milestone here and the one that unblocks the rest, since a scheduled pickup is just the scheduling poller without `pickupLead`. Then scheduled orders + modify/cancel before preparation, order-for-someone-else (recipient fields + recipient-facing tracking), and category expansion — grocery, pharmacy, retail, flowers, package delivery, errands are merchant **categories + order kinds** on the same model, not new modules.

## 10b. GoJoAdmin integration contract (GoJoGo-side seams, build-ready)

GoJoGo's obligation is to make sure that when it's built, it plugs into existing APIs with zero backend rework. The governing rule: **GoJoAdmin gets no private tables and no parallel data path** — everything it does goes through the same public REST surface, so the monolith stays the single system of record and the iOS app could in principle do anything admin can.
